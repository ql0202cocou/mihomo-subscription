## SEC-01 — YAML 标量别名放大字节数

位置：`src/yaml.rs:27`、`src/yaml.rs:69`、`src/converter.rs:187`。

解析前只限制锚点与别名的总数量，解析后只统计节点数与深度，没有统计展开后的标量总字节数。
一个大字符串锚点加 31 个别名，刚好满足 32 的限制，节点数也远小于 10,000，但会复制这个字符串
32 次。输出序列化再把这些内容全部写出，之后还要进行哈希、缓存与 HTTP 响应处理。

本地复现输入 **65,691 字节**，转换输出 **2,097,311 字节**，约 32 倍；转换成功并可进入缓存。
以默认 8 MiB 上游响应限制推算，接近上限的单个标量可以形成接近 256 MiB 的展开内容，尚未计入
Value、克隆、序列化和数据库缓存的额外开销。这个大规模结果是推算，本次未运行该规模的 OOM 实验。

`serde_norway` 的别名跳转限制不能阻止这种输入：这里只有 31 次别名引用，每次引用的是大标量。
仅在输出后增加长度判断也不足以保护已经发生的解析分配。

建议：在展开之前限制标量大小、别名展开总成本与解析事件数量；解析过程中执行统一预算；输出也
设置总字节预算。若暂时无法支持有预算的展开，可先拒绝机场 YAML 的别名，并明确兼容性变化。
解析/转换任务还应有并发预算，避免多个 profile 的大输入同时占满内存。

复现函数：`scalar_aliases_amplify_bytes_without_hitting_limits`。

## SEC-02 — 旧公共请求泄露轮换后的新前缀

位置：`src/generate.rs:180`、`src/generate.rs:207`、`src/settings.rs:35`、
`src/app.rs:98`。

`public_sub` 只在开始时校验前缀和 token，随后可能长时间等待 per-profile 锁；锁内没有重新检查
公开能力是否还有效。重置公共路径先更新内存前缀，再等待各 profile 的锁重生成缓存。此时，已经
通过旧前缀校验的排队请求会被继续处理；如果它触发转换，规则集托管 URL 使用的是新的全局前缀。

已通过真实路由复现以下顺序：

1. 配置含一个被 `RULE-SET` 引用的手动托管规则集，占住该 profile 的刷新锁。
2. 请求旧订阅链接；请求通过入口校验并等待锁。
3. 调用 `POST /api/settings/reset-public-path`，新的前缀已写入内存。
4. 放开锁；旧链接请求得到 `200`，响应的 `rule-providers.url` 包含新前缀。
5. 等待重置 API 返回成功；用旧响应中学到的新前缀及原 token 再请求，仍得到 `200`。

这超出了“轮换无法收回已经下载的内容”的正常边界：旧能力的持有者获得了轮换后的新访问能力，
可以在重置完成后继续下载。若没有托管规则集 URL，或旧请求只读包含旧前缀的缓存，本复现的
新前缀泄露路径不会发生。

建议：为公开能力维护轮换版本，把校验、使用与响应交付关联到同一版本；获得锁后与交付响应前
重新检查前缀/token，失效即统一 `404`。生成时使用同一份能力快照，避免旧授权请求混入新秘密。
token 重置与公开规则集入口也应一并检查相同的生命周期问题；本次直接证明的是全局前缀轮换。

复现函数：`queued_old_public_path_request_learns_rotated_prefix`。

## SEC-03 — YAML 复杂度遍历不完整

位置：`src/yaml.rs:84`。

映射分支只遍历值，不遍历键；`Value::Tagged` 则落入默认分支，完全不遍历它包裹的值。
因此复杂的映射键与带 tag 的序列/映射不受应用声明的深度 32 和节点数 10,000 限制。

本地验证：

- `payload: !opaque [x,x,...]` 包含 10,001 个元素，仍解析成功；去掉 tag 后被拒绝。
- tag 包裹 40 层嵌套，仍解析成功；去掉 tag 后被拒绝。
- 把同样的 10,001 元素或 40 层嵌套放在映射键里，仍解析成功。

这是独立于 SEC-01 的遍历遗漏。底层库自己的递归限制仍存在，不能据此宣称无限递归，但项目
承诺的资源上限确实可以绕过。默认 8 MiB 的原文限制也不能替代解析节点预算。

建议：遍历映射键和值，以及 Tagged 的内部值；若 Mihomo 不需要复杂键/自定义 tag，可直接拒绝。
同时将限制前移到解析过程中，以免先物化巨大的 Value 才拒绝。

复现函数：`tagged_values_bypass_node_and_depth_limits`、
`mapping_keys_bypass_node_and_depth_limits`。

## SEC-04 — 回源失败时刷新节流与合并失效

位置：`src/generate.rs:210`、`src/generate.rs:229`、`src/profile_rule_sets.rs:466`。

订阅是否需要回源只依据成功缓存的 `generated_at`；失败只更新 `last_fetch_*`，并不记录可供节流
使用的尝试时间，也不共享失败结果。等待者拿到锁后看到的还是过期缓存，于是再次回源。
规则集镜像同样只检查成功的 `cached_at`，失败时每个等待者也会依次重试。

本地使用 20 ms 的失败假获取器，验证：

- 公开刷新下限设为 30 秒，10 个并发订阅请求仍产生 **10 次**失败回源，每个响应回退旧缓存。
- 10 个并发远程规则集请求也产生 **10 次**失败回源，无缓存时均为 `503`。

失败不是并发扇出，而是锁内串行重试。默认单次超时 15 秒时，一次 120 请求的突发在不取消请求、
每次耗尽预算的情况下可累积约 30 分钟的排队工作；这是上界场景推算，不是实测耗时。源响应
立即失败时又可以迅速反复回源。公开 token 的持有者能放大机场请求和任务积压，并拖延共享
同一 profile 锁的生成、规则保存或路径轮换。

建议：记录最近尝试时间，不论成功/失败都遵守最小回源间隔；同批请求共享成功或失败结果；
失败设置退避/短期负缓存，有旧缓存则尽快返回。限制等待队列和总体出站并发。

复现函数：`failed_subscription_refresh_does_not_coalesce_or_obey_refresh_floor`、
`failed_remote_ruleset_refresh_does_not_coalesce`。

## SEC-05 — 规则集换源后旧请求重新污染缓存

位置：`src/profile_rule_sets.rs:175`、`src/profile_rule_sets.rs:454`、
`src/profile_rule_sets.rs:504`。

规则集更新会清空缓存，但没有与公开镜像获取共用锁，也没有给定义加版本。已经在途的旧 URL
请求返回后，只按规则集 `id` 写入 `cached_body/cached_at`，可以覆盖刚更新的定义。另一个细节
是 `serve_remote` 在锁前保存 URL，锁内重读行却仍使用旧 URL。

本地通过真实路由与信号量控制获取器复现：

1. 公开规则集请求开始拉取 `https://old.example/rules`，暂停响应。
2. 管理员 PUT 改成 `https://new.example/rules`；接口成功，缓存被清空。
3. 放行旧响应；它把旧内容重新写入同一行。
4. 后续公开请求得到旧内容。数据库 URL 已是新地址，获取器调用次数仍为 1，新源从未被拉取。

旧来源内容会被当作新定义的“新鲜缓存”继续服务，默认可维持 24 小时。若换源是为了撤销已被
入侵的规则供应源，这会让安全修正暂时失效。更新格式时也可能把旧格式字节写到新格式缓存里。

建议：更新与拉取共用规则集锁，或使用定义版本做条件写入；锁内读取并验证最新 URL、source、
cache、enabled 和格式。网络返回后若定义已变化，丢弃旧结果，不能只按 `id` 回写。

复现函数：`old_inflight_fetch_repopulates_cache_after_source_update`。

## SEC-06 — 限流状态无硬上限且清理成本可放大

位置：`src/rate_limit.rs:51`、`src/rate_limit.rs:57`、`src/rate_limit.rs:110`。

`map.len() > 10_000` 只触发过期清理，不限制新桶加入；活跃桶不会被清理。超过阈值后，每次
请求都持有同一把同步 Mutex 全表 `retain`。大量不同来源让状态继续增长，并让单次限流成本
从常数提高到线性；持续加入新地址时，累计成本可接近平方增长。被限流的请求也先做这次遍历。

本地在 60 秒窗口内向限流器送入 15,000 个不同的模拟 IP key，全部获准，没有容量拒绝。
此测试证明状态容量问题；没有在真实网络使用 15,000 个源 IP 实施压力攻击。

攻击不需要知道公开 token，因为下载限流发生在公开校验之前。攻击者仍需要许多真实源 IP，
例如可使用的 IPv6 地址池或分布式来源；这不是单个直连客户端通过伪造 XFF 就能实现的绕过。
实际暴露程度取决于部署是否可从这些来源访问，以及反代是否正确传递可信的真实 IP。

建议：为桶表设硬上限和溢出时的保守限流；把过期清理改为有周期、有预算的工作；增加全局
请求/并发预算。IPv6 可增加前缀级配额，同时保留对普通客户端的公平性。

复现函数：`rate_limiter_accepts_more_than_cleanup_threshold_active_keys`。

## 需要产品决策的风险 — 机场可控制客户端安全配置

位置：`src/converter.rs:185`；当前架构明确要求其余顶层键全部透传。这是现有设计中的风险，
没有把它计入上述 6 个实现缺陷。

转换器可以原样下发机场提供的 `external-controller: 0.0.0.0:9090`、空 `secret`、
`allow-lan: true`、`bind-address: '*'` 和空 `authentication`。本地转换测试确认这些字段
不被拒绝或清除。[Mihomo 官方配置说明](https://wiki.metacubex.one/config/general/)说明这些
字段分别决定控制 API 的监听和认证，以及局域网代理访问。若客户端完整采用该 YAML，机场
就可以改变其安全配置；是否实际生效取决于客户端自己的覆盖策略与防火墙，本次未用客户端验证。

建议明确机场是否被授权控制整个客户端。若只授权提供节点/规则源，采用安全字段白名单，控制
API、认证、监听与下载类配置由管理员模板决定；若要保留完整透传，界面与文档应明确这一信任
前提。`proxy-providers` 的剥离不能替代对其他下载和控制字段的策略。

复现函数：`provider_can_set_client_controller_and_remove_its_authentication`。

## 修复跟进 — 2026-10-05

以上复现结果属于原始 0.6.1 基线。当前工作区已修复 SEC-01 至 SEC-06（尚未发布）：

- YAML 使用带资源预算的 DeserializeSeed，在构建值时限制别名展开，包括映射键/tag；
  合并后的输出 Value 和序列化字节也有上限。小规模锚点/tag 仍兼容。
- 公开订阅/规则集在入口、拿锁后和交付前重新校验能力；管理生成在锁内重读 profile。
- 订阅保存公开刷新完成时间，失败/转换错误同样节流；镜像规则集失败短缓存 30 秒。
- 规则集每次定义更新递增 revision，镜像回写以版本匹配为条件，丢弃旧在途结果；
  排队请求重读最新 URL 并重查全部托管条件。
- 限流器硬限制 10,000 个桶，达到容量拒绝新 key；时间调度清理，不淘汰活跃预算。

新增迁移 `0013_refresh_attempts.sql`；安全回归测试位于 `tests/security_regressions.rs`，
验证失败合并/恢复、排队与在途能力撤销、定义换源/禁用/改名/改格式/关闭托管/删除等场景。
历史 `docs/audits/security-probes-2026-10-05.rs` 保持原样，断言刻意验证旧缺陷，不适用于新实现。
机场控制 API/认证/监听字段透传的设计风险仍存在，处理需要改变现有 API 契约。
